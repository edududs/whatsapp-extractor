# Decisions

Design decisions with their reasons and the alternatives that were considered and dropped. Numbers
are stable; a reversed decision keeps its row and gains a "Superseded by" note.

| # | Decision | Why | Considered and dropped |
| --- | --- | --- | --- |
| D-01 | Read WhatsApp through [neonize](https://github.com/krspy/neonize), a Python binding of Go's whatsmeow. | Multi-device protocol, group and direct chats, contact store, async client, works on Linux and Windows. The session database is whatsmeow's own. | The official Cloud API: cannot read groups the business does not own. Browser automation: brittle and slow. Node bindings (Baileys): a second runtime for a Python project. |
| D-02 | Hexagonal layout with pydantic as the only dependency of `domain` and `application`, enforced by `tests/test_architecture.py`. | Adapters (neonize, SQLAlchemy, rich, typer, tomlkit) can be replaced one at a time; the core is testable without any of them. The test makes the rule executable instead of a convention. | Domain models as SQLAlchemy tables: the schema would dictate the model. Plain dataclasses: the neonize boundary needs validation and immutability. |
| D-03 | `extract` saves a message before it publishes `MessageExtracted`; a writer error stops the extraction, a handler error is logged and isolated. | An event must describe something that already happened. Persistence is the contract; reactions are best effort. | Publish first: events for messages that were never stored. Transactional outbox: no external broker to keep consistent with. |
| D-04 | Ordered in-process `EventBus`, no message broker. | The package is a piece other programs embed. Reactions that need durability read the messages table with their own cursor. | Redis, RabbitMQ, Postgres `LISTEN/NOTIFY`: infrastructure the embedding project may not have, and a second delivery path beside the table. |
| D-05 | Two persistence ports: `MessageWriter` (`save`) is all `extract` needs; `MessageStore` adds `load`. | A Django model, an HTTP client or a queue can be a writer without pretending to support reads. `load` exists so the store contract can verify round trips. | One port with both methods: forces every adapter to implement reads it does not have. |
| D-06 | One process extracts one account; the watchlist of an account is the union of what any consumer needs, and consumers filter by `chat_jid`. | WhatsApp keeps one connection per linked device, so two processes for the same phone disconnect each other. Ingestion decides what is worth keeping; consumers decide what to do with it. | Several accounts in one process: one Go panic would take all of them down. One run per policy: impossible for the same device. |
| D-07 | Each account owns a schema, `wa_<phone>`: a PostgreSQL schema, or an attached file on SQLite. | Isolation without an `account` column in the domain: dropping the schema forgets the account, and two accounts in the same group can store the same message id. `schema_translate_map` makes it one code path. | An `account` column: cross-account queries were not a need, and the primary key would have to grow. One database per account: more to operate for no gain. |
| D-08 | The messages database may differ from the session database (`EXTRACTOR_MESSAGES_DATABASE`). | On hosted PostgreSQL with an HTTP API over `public`, whatsmeow's credential tables would be exposed; the `wa_*` schemas are not. Keeping credentials in a local file and messages on a server is a common layout. | A single database always: forces credentials next to the API surface. |
| D-09 | TOML is the source of truth for settings, written only by the CLI through tomlkit; environment variables carry secrets and deployment overrides. | Watchlists and per-account sections do not fit environment variables. tomlkit preserves the user's comments. The precedence is explicit: overrides, environment, `.env`, TOML, defaults. | Environment-only configuration. YAML: no parser in the standard library and more ways to write the same thing. Writing `.env` from the CLI: mixing secrets with settings. |
| D-10 | Alembic migrations run programmatically at start of `run`, with a version table per account. | Schema evolution needs a history, and the embedding project should not have to run a separate tool. | `metadata.create_all`: no path from one revision to the next. |
| D-11 | Events that carry only a `senderKeyDistributionMessage` are dropped in the source, not deduplicated in the store. | whatsmeow emits one event per encrypted node; the key-exchange node is not a message. Deduplicating by id downstream would hide the cause and still fire an event. | Deduplicate by id in the writer. |
| D-12 | The SQL store keeps the full JSON payload plus indexed projections of `chat_jid` and `timestamp`. | The model evolves faster than a normalized schema; consumers rebuild `Message` with pydantic and query by chat and time, which is what they need. | Fully normalized tables: a migration for every model change. |
| D-13 | A test kit ships in the package under the `testing` extra: Hypothesis strategies, a message factory and `MessageStoreContract`. | A third-party adapter can prove it honors the port with the same tests the bundled ones pass. | Helpers kept under `tests/`: not installable by anyone else. |
| D-14 | `Message` has no account field; the account is process context. | The same message received by two accounts is the same message. Storage provides the namespace (D-07). | An account field on the model: every adapter and every consumer would carry it. |
| D-15 | Media is metadata only; files are not downloaded. | Downloading is a storage, cost and legal decision that belongs to the embedding project. | Downloading to disk or object storage. |
| D-16 | Direct chats carry the contact's saved name; group names are resolved by the `groups` command, not stored on each message. | The contact store is local and cheap to read per message; group metadata needs a network call and changes independently of messages. | A group-name lookup per message. |
| D-17 | Conventional Commits generate the changelog and the release notes through git-cliff; releases are annotated tags turned into GitHub Releases by a workflow. | One source for history, changelog and release notes; no hand-edited changelog to drift. | A hand-written changelog: it drifts from the commits. |
| D-18 | Python 3.13 and 3.14 are both tested in CI; `requires-python` is `>=3.13`. | 3.13 for `asyncio.Queue.shutdown`; 3.14 because embedding projects already run it. Both matrices must pass before a release. | Claiming 3.14 support without testing it. |
